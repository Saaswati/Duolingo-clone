# Assumptions and mocked services

Where the brief allowed a placeholder, this records the line drawn and why —
and what the real version would need.

## Authentication
The brief permits a default logged-in learner, so a single learner is seeded
and identity is resolved from an optional `X-User-Id` header that falls back to
that seed. Every endpoint takes the user as a dependency parameter rather than
reading global state, so replacing this with session auth means rewriting one
function in `app/deps.py`, not the API surface.

## Gems
Display-only. There is no earning or spending path, because a currency with
nothing to buy is scaffolding rather than a feature. The counter is a real
column on `user_stats` and reads through the same code as XP and hearts, so
wiring up a shop would not touch the schema.

## Speech and pronunciation exercises
A placeholder card in Settings. Real pronunciation grading needs speech
recognition plus a scoring rubric, which is a project of its own; a fake
"Correct!" button would have been worse than an honest gap.

## Audio
Spoken prompts use the browser's built-in `speechSynthesis`, and the
correct/incorrect tones are synthesised with the Web Audio API. This means no
audio assets in the repo and any seeded word can be spoken. The voice is
audibly synthetic — a production course ships recorded audio per exercise.

## Leaderboard
Five rivals are seeded with fixed XP. The ranking itself is computed live from
`user_stats`, so the learner genuinely climbs the table as they earn XP; the
competitors simply do not move. A real implementation would scope the query to
a weekly window and a league cohort.

## Streaks and day boundaries
Streaks compare dates, not timestamps, in a single fixed timezone rather than
per-user local time. Correct multi-timezone streak handling is a deeper
problem than it looks and is out of scope here.

The server accepts an `X-Simulated-Date: YYYY-MM-DD` header, exposed in the UI
under **Settings → Time travel**. Streak rules that can only be exercised by
waiting until tomorrow are rules that never get tested; this makes the
increment, the same-day no-op and the reset-after-a-gap all demonstrable in a
few seconds.

## Hearts
Capped at five, one regenerating every thirty minutes. Rather than run a
scheduler, `hearts` is stored alongside `hearts_updated_at` and the current
value is derived on read. Regeneration stays correct even if the server was
asleep — which is what happens on free hosting — and there is no background
worker to deploy. "Practice to refill" is mocked as an immediate free refill.

## Exercise storage
Exercises live in one table with a `type` discriminator and a JSON `payload`
rather than five typed tables. Exercise formats are heterogeneous and add-only,
so this trades relational purity for adding a type without a migration. The
JSON is not unchecked: each type is validated against a Pydantic discriminated
union in `app/schemas.py`.

## Answer checking
Correct answers are never sent to the browser. The `solution` column is a
separate field from `payload` and is excluded from every response schema;
grading happens in `app/services/grading.py` and the client is told only the
verdict, plus the right answer once it has already submitted. This costs one
round trip per question and is the difference between a learning app and a quiz
that can be won with devtools open.

Match-the-pairs is the one exception worth naming: the UI only lets correct
pairs stick, so a wrong tap flashes and clears rather than costing a heart,
which matches the original's behaviour. The server still verifies the submitted
pair ids, so the leniency is a UI choice rather than a hole.

## Course content and multiple languages
The brief allows a single seeded language. Four are seeded — Spanish, French,
German and Hindi — because `seed.py` builds a course from a `LanguageSpec`
(vocabulary, sentences, fill-in-the-blank templates) against a unit and skill
structure defined once. Adding a language is a block of words, not code.

Exercises within a course are generated by rotating through the five builders,
so every lesson mixes recognition, construction and recall. Content volume was
not where the interesting problems in this brief were; the shape of the path
and the loop through it was.

XP, streak and hearts are global rather than per-course. The real app tracks XP
per course; keeping one set of counters kept the leaderboard and streak rules
simple, and nothing in the schema prevents scoping them later.

Spoken prompts use each course's `speech_lang` (`es-ES`, `fr-FR`, `de-DE`,
`hi-IN`), so the browser reads each language with the right voice where the
operating system provides one. Where it does not, playback falls back to a
default voice rather than failing.

## Profile editing
A learner can change their display name, avatar and daily XP goal. The
`UserUpdate` schema contains only those three fields, so earned values — XP,
hearts, streak — cannot be set through the API regardless of what the client
sends. Fields omitted from the request are left untouched.

## Artwork and fonts
The mascot is an original SVG drawn for this project — same round-eyed
friendliness and the same green, our own geometry. None of Duolingo's artwork
is used. Typography is Nunito, the closest freely licensed match to their
Feather typeface.

## Deployment
The hosted backend runs with `SEED_ON_STARTUP=true`. Free hosting tiers have an
ephemeral filesystem, so rather than let the demo come back empty after a
restart, the database rebuilds itself into a known-good state on boot. Progress
persists within a session and resets when the instance restarts. On a paid
instance with a persistent disk, setting the variable to `false` gives
permanent persistence with no other change.

Free instances also sleep after inactivity and take up to a minute to wake. The
frontend shows an explicit "waking the server" message rather than an anonymous
spinner once the wait becomes noticeable.
